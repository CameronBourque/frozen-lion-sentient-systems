# Core mod

The core mod is core's in-game Lua. It signals turns, builds each player's view of the game, runs actions through the game's own request functions, and answers Civilopedia lookups. [findings/lua-contexts.md](../../findings/lua-contexts.md) tracks which Lua state each part runs in.

- **Tagged lines.** Every line the bridge must read has the form `[SENTIENTSYSTEMS] <KIND> <args>`, joined with spaces. `SentientSystems_Print` in `Scripts/SentientSystemsCore_Common.lua` prints them. The tuner adds the state's name in front, so the bridge receives lines such as `SentientSystemsCore_UI: [SENTIENTSYSTEMS] AGENT_TURN 0`. See [findings/tuner-protocol.md](../../findings/tuner-protocol.md#what-we-know-now).
- **Turn events.** The UI script listens for `Events.PlayerTurnActivated` and prints `AGENT_TURN <playerID>` when an agent player's turn starts. One function, `IsAgentPlayer`, decides which players are agent players. For now it picks the human players. When agents can play any slot, only that function changes. The tuner connection carries that line to the bridge.
- **Resync.** `SentientSystems_Resync()` in the UI script prints `AGENT_TURN <playerID>` for each living agent player whose turn is active, the same line the turn event prints. The bridge calls it when it connects, so a restart in the middle of a turn doesn't miss the turn. Between turns it prints nothing.
- **Load line.** Each time the UI script loads, including after a live reload, it prints `CORE_LOADED <state>`, with the state name from `ContextPtr:GetID()`. The bridge logs it, which marks where the core mod started in the log.
- **Load signal.** The UI script prints two lines during a load. `Events.LoadGameViewStateDone` prints `LOAD_READY` when the loading screen shows its button. The tuner carries the line, but runs no commands until the click. `Events.LoadScreenClose` prints `GAME_READY <turn>`, with the turn from `Game.GetCurrentGameTurn()`, when the button is clicked, by the player or by the game. Commands work from then on. The socket resets right after the click, and the line reaches the bridge first. In hotseat and other games where the game clicks the button, the two lines come one right after the other. See [findings/state-list.md](../../findings/state-list.md#state-list-over-a-session).
- **Errors.** `SentientSystems_CatchErrors(name, handler)` in `Scripts/SentientSystemsCore_Common.lua` returns the handler wrapped in `pcall`. Each event handler is added through it, such as `Events.PlayerTurnActivated.Add(SentientSystems_CatchErrors("OnPlayerTurnActivated", OnPlayerTurnActivated))`. When the handler raises a Lua error, the helper prints `ERROR <handler> <message>` in its place. The game's Lua puts the stack trace in the error message, so the line carries the trace without the `debug` library, which UI states don't have. See [findings/lua-contexts.md](../../findings/lua-contexts.md#the-core-mods-states). The helper escapes each backslash as `\\`, each newline as `\n`, and each percent sign as `\p`, so the whole error arrives as one line, and the game's log doesn't read a `%` as a printf format code. The functions the bridge calls, such as `SentientSystems_Resync()`, aren't wrapped, because the tuner already returns their errors to the call. `SentientSystems_Include(name)` in the same file loads a file as `include` does. When the game knows no file by that name, `include` returns an empty list and raises no error, so the helper prints `ERROR include found no file named <name>` instead. That happens when a file is added to the `.modinfo` and the game isn't restarted. See [findings/lua-contexts.md](../../findings/lua-contexts.md#the-core-mods-states). The scripts load every core mod file through it, except `SentientSystemsCore_Common`, which defines it.
- **JSON.** `Scripts/SentientSystemsCore_Json.lua` has `SentientSystems_EncodeJson(value)`, which returns a value as JSON on one line. A table whose keys are 1 to n is a list, and an empty table is an empty list. Any other table is an object with sorted keys, and a number key, such as a unit ID, becomes text. Whole numbers up to 2^53 keep every digit, other numbers keep 14 significant digits, and infinity and NaN become `null`. The encoder escapes quotes, backslashes, and control characters, so text with newlines stays on one line, and writes each percent sign as `\u0025`. The game's log prints text as a printf format, where a `% s` crashed the game, so the printed text holds no `%`, and `JSON.parse` reads it back. See [findings/tuner-commands.md](../../findings/tuner-commands.md#what-we-know-now). A function, a userdata, a boolean key, or a table that holds itself raises an error that names where, such as `value.cities[1].name`.
- **Stash.** A command whose output is longer than about 2 MiB gets no reply, and the connection stops answering. The limit counts all of a command's prints together. See [findings/tuner-commands.md](../../findings/tuner-commands.md#what-we-know-now). So long text crosses in several commands. `SentientSystems_Stash(text)` keeps the text in pieces of at most 1,000,000 bytes, in place of any earlier stash, and prints how many there are. The bridge then sends `SentientSystems_PrintPiece(<n>)` once for each piece and joins the pieces. After the last piece, the stash is cleared. The bridge decodes each print as UTF-8 on its own, so a piece never ends inside a UTF-8 character.
- **Version report.** `SentientSystems_GetVersion()` in the UI script reads `<Properties><Version>` from the mod's `.modinfo` and prints `CORE_VERSION <version>`. See [versioning.md](../versioning.md#release-flow).
- **State serializer.** It builds a view of one player's game from that player's own visibility data, never from what is on screen. A map reveal that changes only the view can then never leak hidden information to an agent. A reveal that writes the player's visibility data, such as FireTuner's **Reveal All**, does leak it. See [findings/game-state.md](../../findings/tile-visibility.md#firetuners-map-reveal). The view holds what a player sees on these screens, grouped by screen. The table below lists what it holds now, and the [roadmap](../../roadmap/README.md) says when the rest comes:
  - **The map.** Revealed tiles, the player's units, and the rival cities and units the player can see.
  - **The city panel, and the City Status tab of Reports.** Each city's yields, growth, housing, amenities, loyalty, defense, districts, production, growth rate status, war weariness, and governor.
  - **The Next Turn button.** What blocks the end of the turn.
  - **The top bar.** The gold and faith balances, the science, culture, faith, gold, and tourism per turn, the trade route capacity, and, with Gathering Storm, diplomatic favor.
  - **The Yields tab of Reports.** Income by source, building and unit upkeep, deal payments, and net income per turn.
  - **The Resources tab of Reports.** Strategic and luxury resources, and, with Gathering Storm, strategic stockpiles.
  - **The Gossip tab of Reports.** What the player has heard about met players.
  - **The Era Progress panel.** The era, era score, current age, the thresholds for the next age, turns until the next era, and the active effects.
  - **The Great People screen.** Each candidate's era and effect, each met player's recruit progress, points per turn, and the gold and faith patronage costs.
  - **The City-States screen.** Envoy tokens, the bonuses of each kind of city-state, and each city-state's envoys, suzerain, suzerain bonus, resources, quests, and the players with envoys there.
  - **The Governors panel.** The appointed governors, their cities, and their promotions.
  - **The Religion screen.** The pantheon, the religion, and its followers.
  - **The diplomacy screens.** War or peace with each met player, proposed deals, relationships, grievances, and agendas.
  - **Their own screens.** Trade routes, spies, great works and tourism, and climate and disasters.
  - **World Rankings and the leader panel.** The scoreboard and victory progress, as World Rankings shows them, and each met player's score, military strength, and science, culture, gold, and faith per turn, as the leader panel at the top right shows them. Every player is listed in the screen's order. A met player has their ID and the values the screen shows, and an unmet player has only their place, as the screen shows a `?` icon.

  A feature that isn't in the ruleset, such as loyalty without the Rise and Fall expansion, is left out.

  `SentientSystems_GetState(playerID)` in `Scripts/State/SentientSystemsCore_State.lua` returns the view as JSON, and the UI script loads it with `include`. Each section of the view has its own file in `Scripts/State/`, such as `SentientSystemsCore_StateCities.lua`, which defines one global, such as `SentientSystems_GetCityStates(player)`. The state file loads each one and puts the sections together. The bridge reads it through the stash. The shape of each section is in the schemas in [packages/core/bridge/src/state/](../../../packages/core/bridge/src/state/).

- **Choices.** `SentientSystems_GetChoices(playerID)` returns the legal options for each discrete choice as JSON, in a call of its own, so the agent reads them only when it decides. They include production and gold, faith, and tile purchases for each city, techs, civics, policies, and the options for each other end-turn blocker. An option lists what its screen shows, such as turns to complete, boost status or the boost requirement, resource requirements, and prerequisites. Tile purchases list the tiles to buy, and the tiles where a district or a wonder can go come from the placement call. An item the screen greys out is listed with the screen's reason, in the game's language, and with its text key where the game gives one. Each blocker in the state names the choice that resolves it. `SentientSystems_GetChoices` is in `Scripts/Choices/SentientSystemsCore_Choices.lua`, which the UI script loads with `include`, and the bridge reads it through the stash. Each choice has its own file in `Scripts/Choices/`, such as `SentientSystemsCore_ChoicesProduction.lua`, which defines one global, such as `SentientSystems_GetProductionChoices(player)`. The choices file loads each one and puts them together. The production choice counts the tiles from the placement file to decide what the panel greys out. The calls are in [findings/game-choices.md](../../findings/game-choices.md), those for the government and policies in [findings/game-government.md](../../findings/game-government.md), and those for religion in [findings/game-religion.md](../../findings/game-religion.md), those for envoys in [findings/game-city-states.md](../../findings/game-city-states.md), those for great people in [findings/game-great-people.md](../../findings/game-great-people.md), those for captured cities in [findings/game-captured-cities.md](../../findings/game-captured-cities.md), those for spies in [findings/game-spies.md](../../findings/game-spies.md), and those for artifacts in [findings/game-artifacts.md](../../findings/game-artifacts.md), those for governors in [findings/game-governors.md](../../findings/game-governors.md), those for dedications in [findings/game-dedications.md](../../findings/game-dedications.md), those for emergencies in [findings/game-emergencies.md](../../findings/game-emergencies.md), and those for the World Congress in [findings/game-world-congress.md](../../findings/game-world-congress.md). The choices so far:

  | Key | Holds |
  | --- | --- |
  | `emergencies` | The emergency the player has to look at, as the emergency popup offers it, there only while the emergency blocker is up. It holds one entry, with `type`, such as `EMERGENCY_CAPTURE_CITY_STATE`, `name`, `description`, and `goal`, `target`, the target's player ID, `targetCity`, `hostile`, `turnsLeft`, negative for a finished one, `succeeded`, for a finished one, `options`, `join` and `reject` for an emergency that hasn't begun and `acknowledge` for any other, `members`, `goals`, `scoring`, left out for the target, `buffs`, and `rewards`, with `members` and `target`. Checked against an ongoing emergency's popup in a running game, though not the blocker's own case, with `join` and `reject` |
  | `worldCongress` | What the player decides in a World Congress session, and looks at when one ends, as the congress screen shows it. It has `favor`, and, in a session, only while its blocker is up, `session`, `regular` for one with resolutions and `special` for one without, `voteCosts`, the Favor for 1, 2, and so on up to the most votes, in total, `resolutions`, each with `type`, `name`, `options`, with `A` and `B`, `targetType`, `targets`, each with `index`, the number a vote sends, `name`, and `player` for a player, and `favored` and `disfavored`, and `proposals`, each with `type`, `name`, `description`, `sender`, and `target`. Out of a session it has `available`, the proposals the player could call a Special Session for, each with `cost` and `disabled`, and, at the results blocker, `session` `review`, `results`, with `votes` and `voters`, each player's vote, and `effects`, with `turnsLeft`. The results of a session's proposals aren't included |

- **Placement.** `SentientSystems_GetPlacement(playerID, cityID, type)` in `Scripts/Placement/SentientSystemsCore_Placement.lua` returns where a city can place one district or wonder as JSON, in a call of its own, as the placement view shows the tiles once the player picks one. The UI script loads the file, and the bridge reads the call through the stash. It raises an error for an ID with no player or city, and for a type that isn't a district or a wonder. The calls are under **Placement tiles** in [findings/game-choices.md](../../findings/game-choices.md).

  | Key | Holds |
  | --- | --- |
  | `tiles` | The tiles the city owns where the district or wonder can go now, each with `x`, `y`, and, for a district, `adjacency`, its bonus there by yield, such as `{"science":3}`, when it has one |
  | `purchaseTiles` | The tiles the city could buy where it could go, in the same form. It lists every tile to buy, while the panel counts a district's tile to buy only when it has a bonus. Neighborhood housing isn't included |

- **Tech and civic trees.** `SentientSystems_GetTechTree(playerID)` in `Scripts/Trees/SentientSystemsCore_TreesResearch.lua` returns the tech tree as the tree screen shows it, as JSON, in a call of its own, so the agent reads it only when it plans a route. The UI script loads the file, and the bridge reads the call through the stash. It reads the tree from the running game, because the Tech and Civic Shuffle mode changes it, and the details of each node come from the same reader as the tech choice. `SentientSystems_GetCivicTree(playerID)` in the same file returns the civic tree in the same form, with `researched` counting civics. The civic tree leaves out the screen's extra icons for envoys and governor titles. The calls are in [findings/game-choices.md](../../findings/game-choices.md).

  | Key | Holds |
  | --- | --- |
  | `nodes` | Every node of the tree, in the tree's order, each with `type`, `era`, `status`, one of `researched`, `current`, `ready`, and `blocked`, `cost`, and `prerequisites`, by type. `turns` is there while it is above 0 and the node isn't researched, and for the node in research it is the turns left. `progress`, `boost`, `unlocks`, `description`, and `recommended` are as in `techs`, and the screen shows no boost, progress, or advisor's pick for a researched node |
  | `nodes`, unrevealed | A node that the screen shows as **Unrevealed**, in the Tech and Civic Shuffle mode, has a `type` such as `?1`, numbered in the tree's order, and only `era`, `status`, `turns`, `progress`, and `prerequisites`. The screen shows no name, cost, boost, or unlocks for it. Other nodes' `prerequisites` name it by its number, as the screen's lines link it, and the numbers hold only within one read |
  | `players` | The player and each player they have met, as the timeline at the bottom of the screen marks them, each with `player`, an ID, `researched`, the number of nodes they have researched, and `era`, the latest era they have researched in, left out when they have researched nothing |
- **Governor tree.** `SentientSystems_GetGovernorTree(playerID)` in `Scripts/Trees/SentientSystemsCore_TreesGovernors.lua` returns the governors and their promotion trees as the Governors panel and its details panel show them, as JSON, in a call of its own, so the agent reads it only when it chooses a governor to appoint or a promotion to give. The UI script loads the file, and the bridge reads the call through the stash. It includes the Secret Societies the player has discovered, and leaves out the governors the player could never appoint, and, like the state, is empty without Rise and Fall. The calls are in [findings/game-governors.md](../../findings/game-governors.md).

  | Key | Holds |
  | --- | --- |
  | `governors` | Each appointed governor in the panel's order, then each governor the player could still appoint, each with `type`, such as `GOVERNOR_THE_MERCHANT`, `name`, `title`, `description`, `status`, `appointed` or `candidate`, `turnsToEstablish`, the turns they take to settle in a city, `loyalty`, the loyalty pressure they give, and `promotions`. A Secret Society has `secret`, `true`, and neither `turnsToEstablish` nor `loyalty`, as its card shows no stats |
  | `governors[].promotions` | The governor's promotions in the game's order, each with `type`, `name`, `description`, `level` and `column`, its place in the tree, `requires`, the types of the promotions it follows, and `status`. A promotion needs any one of the promotions in `requires`, not all of them, and the base ability, at level 0, has none. `status` is `held`, for one the governor has, `available`, for one they can earn now, and `locked`, for one that needs a prerequisite first. A candidate holds only its base ability, as its card shows. A promotion of a Secret Society that the panel hides until the one before it is held has `hidden`, `true`, and the game's own text for an unknown promotion, `???`, in its `name` and `description`. Its `type` is numbered, such as `GOVERNOR_PROMOTION_OWLS_OF_MINERVA_2`, and gives nothing away |
- **Action API.** Each action wraps the request function the game's own UI calls, and the game checks legality. A failed action returns its reason. The reason comes from the game's check where it gives one, and from the API's own messages for common cases. The game's UI Lua files ship as plain text and show which call each screen makes. See [findings/game-api.md](../../findings/game-api.md).
- **Checkpoint ID.** A gameplay script writes the checkpoint ID described in [memory.md](../memory.md#checkpoint-ids).
- **Civilopedia lookup.** It queries the `GameInfo` tables and localized text at runtime, so DLC and other mods are included. It also reads the Civilopedia's Concepts section for general rules such as movement, combat, and terrain.

## Decisions

| Decision | Reason |
| --- | --- |
| State comes from the player's visibility data, not the screen | A map reveal that changes only the view can never leak to an agent |
| The choices list the legal options for discrete choices, and the placement call the tiles for a district or a wonder | Saves wasted calls. Those tiles are few, so a list beats guessing. Moves and attacks have too many targets to list, so they return failure reasons instead |
| The tiles for districts and wonders are a call of their own, for one district or wonder | Tiles were about two thirds of the production choice, and a mid-game empire would send about 100 KB of them. The agent needs the tiles only for the one item it places, as a player sees them only after picking one |
| The choices are a call of their own, not part of the state | Production options for every city are large, and the agent needs them only when it decides. Keeping them out of the state keeps each turn's context small |
| A greyed-out option carries the screen's own text | It needs no upkeep and matches what a player reads. Our own codes would need a mapping for every reason, including those from DLC and mods. If agents misread the text, codes come next |
| The trees are calls of their own, built from the running game | The agent reads a tree only when it plans a route. The Tech and Civic Shuffle mode changes the tree, so static data can be wrong |
| The scoreboard lists unmet players as places only | World Rankings shows how many players there are, their order, and whether an unmet one leads, but not who they are |
| Every failed action returns a reason | The agent can decide again instead of repeating a mistake |
| Tile contents come from the live plot, as the tooltip shows them, not from the visibility layers | A player learns a tile's contents by hovering over it. The map's resource icons come from the player's `RESOURCES` layer, which stays empty on tiles revealed without being seen, such as around a rival's city. The tooltip still shows those resources |
| The state includes the scoreboard and victory progress | A human sees it, and sweat levels measure against it |
| Find the state size by measurement | No useful budget exists before the first full game |
| Game facts come from the Civilopedia at runtime | It includes DLC and mods with no upkeep |
| Lines for the bridge start with `[SENTIENTSYSTEMS]` | The tuner carries every print from every state, including the game's and other mods'. The tag lets the bridge pick out its own lines, and another mod's `AGENT_TURN` print can't start an agent turn |
| A file that `include` can't find prints an `ERROR` line | `include` returns an empty list with no error. The first sign would come later, as a call to a `nil` function, with nothing to say which file is missing |
| Event handlers report Lua errors as tagged `ERROR` lines | An uncaught error reaches the bridge only as an untagged game line, which it ignores. The bridge would wait for a turn signal that never comes, and nothing would say why |
| The error helper uses `pcall`, not `xpcall` with `debug.traceback` | The error message already holds the stack trace, and UI states have no `debug` library. `pcall` also passes the handler's arguments, so the helper needs no closure |
| The error helper and the JSON encoder escape the percent sign | The game's log prints text as a printf format, so a raw `%` prints garbage, and a `% s` crashed the game. `\u0025` is plain JSON, so the bridge needs nothing for it, and an error line's `\p` sits beside its other escapes |
| The error helper escapes newlines and backslashes | The tuner sends each line of a print as its own line, and only the first one has the state's name. Without the escapes, the trace would arrive as untagged lines |
| The turn signal comes from the UI state | The gameplay and UI events both fire once per human turn. The bridge already calls the UI state for the version report and for actions |
| Each mod file name starts with the mod's prefix, such as `SentientSystemsCore_` | `include` finds a file by name among every enabled mod's imported files, so a generic name can load another mod's file |
| The JSON encoder sorts object keys | The same state gives the same text, so tests and logs can compare it |
| An empty table encodes as an empty list | Lua can't tell an empty list from an empty object. Lists, such as units or promotions, are often empty, and objects rarely are |
| Long JSON crosses in pieces of 1,000,000 bytes, one command each, from a stash | A command whose output passes about 2 MiB gets no reply and stops the connection, however many prints it makes. The stash encodes the state once. A 1 MB print arrives in about 40 ms |
| Each state section has its own file in `Scripts/State/` | The state grows with every section, and one file would pass 1,000 lines. A file per section keeps each one and its tests small. `include` finds a file by name in any folder, so the folder only groups the files |
| The core mod has no gameplay script until checkpoint IDs need one | Nothing else needs a gameplay state yet |
| The load signal is two tagged lines from the loading screen's events | The bridge keeps its rule that it reads only tagged lines. `LOAD_READY` comes before the click, so the bridge can start the new game's log file there, and a later tool can press the button. `GAME_READY` reaches the bridge before the socket resets, so it needs no resync |
