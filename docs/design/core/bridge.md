# Bridge

The bridge is one TypeScript program that connects to the game over FireTuner, runs the agent loop through an MCP server, calls the model, and stores agent memory. It ships as a single executable.

- **Tuner client.** It connects to the FireTuner socket, which the game opens when `EnableTuner` is `1` in `AppOptions.txt`. It sends Lua to run and reads console output. The protocol has no official documentation. The community reverse-engineered it, and phase 0 confirmed it. See [findings/tuner-protocol.md](../../findings/tuner-protocol.md) and [findings/tuner-commands.md](../../findings/tuner-commands.md). The client is three layers in `src/tuner/`. `framing.ts` turns bytes into frames. `connection.ts` holds the socket and reconnects with backoff. `client.ts` does the handshake, finds Lua states by name, and runs Lua. It sends one request at a time, and wraps each command in the marker wrapper from `wrapper.ts`. Only lines between a command's markers, from the command's own state, are its result. Every other print goes out as an `output` event.
- **Tagged lines.** `src/events.ts` turns the core mod's [tagged lines](in-game-lua.md) into typed events, such as `{ type: "turn", playerId: 0 }`. `readLine` in the same file strips the state name from a line, parses it, and logs the event. `src/main.ts` passes each `output` line to it. A line without the tag comes from the game or another mod, and the bridge ignores it. A tagged line with an unknown kind or bad arguments gets a warning in the log. An [`ERROR` line](in-game-lua.md) becomes a `core_error` record at the `error` level, with `handler`, `message`, and `traceback` fields. The bridge undoes the core mod's escapes, splits the text at the `stack traceback:` line, and cuts each path to start at `Sid Meier's Civilization VI\`. The cut covers both the `My Games` folder and the game's install folder. The core version line comes back in the lines of a `run()` call, not as an `output` event.
- **Resync on connect.** When the bridge starts or reconnects, it asks the game whose turn it is. After the version call, `src/connect.ts` calls `SentientSystems_Resync()`, which prints `AGENT_TURN` for each agent player whose turn is active, and nothing between turns. If the version call fails, the resync is skipped, since it would fail the same way. Events cover everything after that. Without this step, a bridge restart in the middle of a turn misses the turn-start event.
- **Load reset.** `src/game-load.ts` handles the [load signal](in-game-lua.md). On `LOAD_READY`, the bridge starts a new log file, as [logs.md](logs.md) describes. On `GAME_READY`, it drops the client's state list with `forgetStates()`, so the next command lists the states again. `src/main.ts` passes the handler to `readLine` as `onEvent`, which runs before the event is logged, so the `LOAD_READY` record is the first line of the new file. Later, `GAME_READY` also cancels any agent turn from the old game.
- **Version check on connect.** The bridge and the core mod share one version and release together. When the bridge connects, `src/connect.ts` calls `SentientSystems_GetVersion()` in the core mod's state, and the bridge logs the version. For now it only logs it. A failure, such as the core mod's state missing at the main menu or the game not answering during a load, logs a warning that says what to do, and the next connect tries again. On a mismatch, the bridge asks the user to update, then downloads the GitHub release that matches the core mod. If that release is missing, it offers the newest release with the same MAJOR version. It verifies the download, replaces itself, and restarts. Resync on connect makes the restart safe in the middle of a session. Feature mod checks are in [versioning.md](../versioning.md#runtime-checks).
- **Stash reader.** `readStash(client, call, schema, what)` in `src/stash.ts` reads JSON that the core mod keeps in its [stash](in-game-lua.md). It sends `SentientSystems_Stash(<call>)` to `SentientSystemsCore_UI`, reads the piece count, sends `SentientSystems_PrintPiece(<n>)` for each piece, and joins the pieces with nothing between them. A `zod` schema checks the JSON and gives it its type. Every failure comes back as `{ ok: false, error }`, with what went wrong: a missing core mod, a timeout, a Lua error, invalid JSON, or each field that doesn't match the schema. `what` names the JSON in the error, such as `state`.
- **State.** `readState(client, playerID)` in `src/state/state.ts` reads one player's [state](in-game-lua.md) through the stash reader, with the call `SentientSystems_GetState(<playerID>)`. The schema isn't strict, so a field from a newer core mod is dropped instead of failing the whole state. Each section's schema has its own file in `src/state/`, such as `cities.ts`, to match the core mod's file for that section in `Scripts/State/`.
- **Choices.** `readChoices(client, playerID)` in `src/choices/choices.ts` reads one player's [choices](in-game-lua.md) through the stash reader, with the call `SentientSystems_GetChoices(<playerID>)`. Its schema drops unknown fields in the same way, and each choice's schema gets its own file in `src/choices/`. The core mod encodes an empty table as an empty list, so an empty list reads as no choices.
- **MCP server.** It exposes the action API and lookup as tools to the agent loop.
- **Model client.** It calls the configured provider through one interface, the Vercel AI SDK, so any provider works. `models.yaml` maps each provider and operation to a model. Testing fills that table.
- **Memory store.** It reads and writes each agent's memory files and snapshots them under the current checkpoint ID. See [memory.md](../memory.md).

The agent and advisor features are modules in the same codebase, not plugins. The logs are in [logs.md](logs.md), the config file is in [settings.md](settings.md), and the build and the tools that work on the code are in [toolchain.md](toolchain.md).

## Decisions

| Decision | Reason |
| --- | --- |
| `readState` and `readChoices` return failures instead of throwing them | A state can fail for ordinary reasons, such as a game that is loading. The agent loop decides what to do, and a bad state never crashes the bridge |
| The state and choices schemas drop unknown fields | The bridge and the core mod release together, but a user can update one first. Dropping a new field keeps the rest of the state usable |
| The bridge is one TypeScript program, with no plugin system | TypeScript has the reference MCP SDK and builds a single executable. Two consumers do not justify plugins |
| Any LLM provider, through one interface | Users bring their own provider. Testing decides which models are good enough |
| Resync and version check when the bridge connects | A restart can miss events, and the mod and bridge update separately |
| The bridge updates itself to the mod's version, after the user agrees | Nontechnical users should not install updates by hand. A matching version beats the latest one |
| The tuner client has three layers: framing, connection, and client | Each layer is tested on its own. Framing does no input or output, and the connection knows framing but not the protocol |
| Each command runs inside the marker wrapper | Replies carry no request ID, and an unprompted print looks the same as a command's output. The markers tie each line to its command. The wrapper is one expression, so it runs whichever way the game runs a command |
| One request at a time, through one queue | Replies carry no request ID. A round trip takes 18 to 54 ms, which is small next to a model call |
| A request that times out keeps the socket open, and its late reply is dropped | Replies always come back in order. A load holds every reply for about a minute, so dropping the socket on each timeout would reconnect over and over |
| The client keeps the state list for each connection, drops it on `GAME_READY`, and lists the states again after `ERR:Invalid Lua State` or a `ContextPtr:GetID()` mismatch | A load resets the socket, which clears the list, and `GAME_READY` clears it for a load that keeps the socket. The reset comes a few milliseconds after `GAME_READY`, so a list request sent then would be cut off, and the next command lists the states instead. A quit to the main menu keeps the socket open, so the client catches a stale index when a command uses it |
| The bridge reads a tagged line from any Lua state | A list of allowed states would need upkeep for each new script. Anything else the bridge needs goes into a tagged line where it can. An untagged game line that the bridge must read is an exception |
| A tagged line that doesn't parse logs a warning | A core mod newer than the bridge, or a Lua bug such as a `nil` player ID, shows in the log. Without it, an agent would never act and nothing would say why |
| Paths in a Lua error start at the game's folder, at every log level | The part cut off is always one of two known folders, so it doesn't help debugging, and it holds the user's name. If the level changed what an error record holds, one event would look different in two logs |
| A failed call on connect logs a warning, and the bridge keeps running | The core mod's state is missing at the main menu, and the game doesn't answer during a load. A load resets the socket, so the next connect runs the calls again with no retry loop of its own |
| Reconnect with backoff, from 500 ms up to 10 s | The game may not be running yet. After a crash it listens again under a new process, and the bridge should find it without a restart |
